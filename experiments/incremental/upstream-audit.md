## Genuine export workflow

Lean 4.35 includes `leanexport`; it uses the compiler's matching export representation. Upstream's regression test `tests/lake/tests/check-from-export/test.sh` uses this exact workflow:

```sh
# In a Lake project pinned to leanprover/lean4:v4.35.0:
lake build Solution
lake env leanexport Solution -- comm > solution.ndjson
leanchecker --from-export solution.ndjson
lake check --from-export solution.ndjson
lake check --from-export solution.ndjson --paranoid
```

`Solution` is the module, `comm` is an existing compiled declaration, and the exporter recursively includes its dependencies. Several roots may follow `--`. Without `--`, it exports all non-internal declarations from the imported module environment. All modules must already be built. `lake env` supplies the project search path, and running the exporter under the correct toolchain ensures its internal `lean --print-prefix` query finds compatible core oleans.

The independently built equivalent is:

```sh
lake env /absolute/path/to/lean4export/.lake/build/bin/lean4export Solution -- comm > solution.ndjson
```

Use the `v4.35.0` exporter commit above, not the inspected clone's initial v4.36.0-rc1 HEAD. The built-in exporter emits metadata with exporter `lean4export` 3.1.0, format 3.1.0, Lean `4.35.0`, and Lean githash. Preserve the raw file and its SHA-256. The metadata is provenance text rather than a certificate: the official parser currently discards its first line instead of validating the claimed hash/version.

Both exporters can report an unknown requested constant through `panic!` text while returning zero (documented and checked by con-leche's `scripts/natop-matrix.sh`). A harness must check stderr for `Constant ... not found in environment`, verify all intended roots are present, require nonempty output, and reject partial/failed exports. The default excludes unsafe declarations; `--export-unsafe` is available for negative tests.

## Exact export oracle versus olean checking

Lean 4.35's direct command is:

```sh
leanchecker --from-export /absolute/path/to/case.ndjson
```

This parses the NDJSON and replays the declarations into an empty `Lean.Kernel.Environment`. `Lean.Kernel.Environment.replay` calls `addDeclCore 0 0`, which reaches the official C++ kernel. It reconstructs inductive declarations, then compares supplied constructor and recursor information with kernel-generated information. `LeanChecker.checkExport` also checks the original exported quotient constants against those generated by the kernel, after removing `Quot.mk`, `Quot.lift`, and `Quot.ind` from the replay map to avoid duplicate installation.

This is suitable as a second implementation oracle on precisely the same retained export file supplied to con-ron/con-leche. It does not require a custom arena wrapper or an olean conversion. It still shares the Lean frontend's export parser and runtime, which is why retaining a Rust checker and raw-byte evidence is useful.

Direct checker outcomes:

- `0`: replay and quotient post-check accepted.
- `1`: replay rejected, quotient post-check rejected, or ordinary top-level IO/parser failure. Keep stderr/stdout and distinguish parser/infrastructure failures from a mathematical rejection in the harness.
- timeout, signal, or any unexpected code: error, never an accept.

The command without `--from-export` checks oleans and has different semantics. `leanchecker Module` replays declarations from modules onto their imported environment; `leanchecker --fresh Module` replays a single module's full imported environment into a fresh environment. These are not evidence that a separately retained/mutated export was checked. Use `--from-export` for differential checking of exact exports.

Replay intentionally skips unsafe/partial constants, and the official kernel assumes standard built-in constants. The Lean Kernel Arena explicitly limits `Init.Prelude` cases to absence or official-release declarations; custom redefinitions of these names fall outside its expected oracle contract.

## What Lake 4.35 actually runs

`lake check` builds default targets, exports them, runs kernel(s), and rejects nonstandard axioms. `lake check --from-export FILE` skips the project build/export and checks that file. Upstream help explicitly says this establishes acceptance of the export and nothing about the current project. In this mode no `lake-manifest.json` is required and no project oleans are loaded into Lake's address space.

The default checker command is:

```sh
<toolchain>/bin/leanchecker --silent --from-export FILE
```

`--paranoid` adds these bundled executables, in this order, before the default checker:

```text
leanchecker-paranoid --silent --from-export FILE
lean4lean --import FILE
nanoda_bin NANODA_CONFIG_JSON
con-leche FILE
con-ron FILE
leanchecker --silent --from-export FILE
```

The nanoda JSON is generated by Lake and contains `export_file_path`, `use_stdin: false`, `permitted_axioms`, `unpermitted_axiom_hard_error: false`, `num_threads: 4`, `nat_extension: true`, and `string_extension: true`. For a stand-alone exact-stream runner a config with the same fields gives a direct invocation. Con-leche and con-ron default to verified mode in the inspected current sources; an explicit `--verified` is clearer for standalone evidence.

Lake outcomes, documented in `src/lake/Lake/CLI/Help.lean:539`:

- `0`: all selected kernels accepted and only standard axioms were used.
- `1`: kernel nonzero, nonpermitted axiom, build failure, or caught runtime failure.
- `2`: could not start, e.g. missing sandbox, missing manifest when building, missing/default-target problem, or absent input file.

Lake treats **every** checker nonzero as failure. It does not preserve arena's `2 = decline` meaning; direct checker results must be retained separately. The arena convention for con-ron/con-leche is `0 accept`, `1 reject`, `2 decline`, `3 error` (other codes also error). A decline cannot be counted as either acceptance or a successful negative test.

Lake additionally rejects any axiom outside `propext`, `Classical.choice`, and `Quot.sound`. Direct C++ kernel checking permits well-typed axiom declarations; the two commands therefore answer different questions for negative fixtures containing arbitrary axioms or `sorryAx`.

Lake uses `bwrap` even for `--from-export`. The environment has `/usr/bin/bwrap`, but successful namespace creation has not been tested by this subtask. If namespaces are blocked, report a sandbox/infrastructure limitation, then use the direct official C++ command for the exact-export oracle. `--inadvisably-no-sandbox` exists and emits an untrustworthy-run warning; do not silently label that equivalent to a sandboxed Lake check.

The source build's external checker targets are excluded from the default CMake `ALL`; release CI builds them explicitly. Therefore a source-built Lean might lack the bundled external commands. Check each binary's existence in the actual installed release before promising all six runs. At report-writing time the parent's Lean installation was still in progress, so practical binary availability remains for the parent to record.
